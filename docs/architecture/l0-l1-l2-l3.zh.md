# L0/L1/L2/L3 分层模型

L0/L1/L2/L3 是 Context Compiler 的产品和查询心智模型，不是编译 pipeline stage。Pipeline stage 描述系统怎么执行；L0/L1/L2/L3 描述用户和 Agent 怎么从项目资料一路钻取到语义理解。

```txt
原始 sources
  -> L0 Package：资料包级别分类
  -> L1 SourceGroup：包内文件和目录的局部归组
  -> L2 LocalGraph：以 L1 group 为边界构建局部图
  -> L3 SemanticGraph / ClaimGraph：链接和融合多个 L2 局部图
```

## L0 Package

L0 是资料包级别分类，也是用户和 Agent 的第一入口。它回答的问题是：这个项目里有哪些可用材料？

一个 L0 package 可以代表代码仓库包、产品文档包、设计资料包、API 合同包、测试资料包、运行时数据包、分析资料包、资产包或 unknown 包。L0 的原则是资料不能丢，即使暂时无法准确分类，也应该进入 unknown 或 other package，后续再通过 evidence 和 correction 修正。

L0 应该呈现为项目级 package map 或 package list。每个 package 至少展示名称、类型、路径、摘要、文件数、L1 group 数、build unit、adapter selection、置信度、分类来源、诊断和修正入口。

## L1 SourceGroup

L1 是对 L0 包内部文件、目录或资料的局部归组。它回答的问题是：这个 package 内部有哪些边界可以独立处理？

L1 的目标不是做漂亮分类，而是切出足够小、足够一致、可以独立建图的 SourceGroup。一个代码仓库可以是一个 group，一个同领域文档目录可以是一个 group，一批 API 合同可以是一个 group，一组运行时数据也可以是一个 group。

L1 应该呈现为某个 L0 package 下的可钻取 group 列表。每个 group 至少展示 id、路径、类型、boundaryMode、childrenPolicy、summary、confidence、decisionSource、sourceRef、build unit 和 adapter selection。

## L2 LocalGraph

L2 是以每个 L1 SourceGroup 为边界构建出来的局部图。它回答的问题是：这个局部边界内部有哪些真实事实、结构、关系和证据？

L2 不是再做一轮归组，而是把 L1 group 交给合适的 adapter 建成本地图。代码 group 可以产生 File、Module、CodeSymbol、Route、import/call/reference 等节点和边；文档 group 可以产生 Document、Section、Requirement、BusinessRule、Decision、Risk 等节点和边；API group 可以产生 APIEndpoint、RequestDTO、ResponseDTO 等节点和边。

L2 的重点是保真。它应该保留 sourceRef、provenance、adapter selection reason、diagnostics、local indexes 和可解释的 evidence chain。L2 不要求先有全局语义推理才能正确工作。

L2 应该呈现为 build graph scope。用户从 L1 group 进入后，默认看到的是一个或多个 L2 标准图入口，而不是直接看到文件、目录、Requirement、Document 或 CodeSymbol。打开 L2 图以后，才进入文件、内容节点、符号、文档事实、局部边、诊断、source trace 和 evidence。

## 内部标准格式

第三方组件应该负责构建或辅助构建图，但第三方结果不应该直接成为系统默认图层。推荐流程是：

```txt
third-party raw output
  -> raw artifact / adapter fact
  -> L2 domain IR
  -> ContextGraph projection
  -> viewer / MCP / query surface
```

因此，标准格式不是“只有一种大而全的语义图”，而是：

- 一种统一外壳：`ContextGraph`，负责节点、边、scope、sourceRef、provenance、evidence、diagnostics、索引和查询传输。
- 多种 L2 领域标准图：例如 `RepositoryGraph`、`SemanticCorpusGraph`、`ApiContractGraph`、`InventoryGraph`。代码、资料、API、测试和运行时资料的结构不同，不能强行压成同一种内部 schema。

L3 可以再收敛到更统一的跨图链接或 Claim 格式；L2 阶段优先保留领域结构和证据链。

## L3 SemanticGraph / ClaimGraph

L3 是跨多个 L2 LocalGraph 的全局语义融合层。它回答的问题是：不同资料、代码、接口、测试和运行时信号之间共同支持什么语义判断？

L3 不应该只是把 L2 节点再复制一遍。L3 的核心单元建议是 Claim。Claim 是带证据、置信度、状态、适用时间、反证和版本历史的语义断言。它可以表达需求和代码实现的覆盖关系、API 和页面的影响链、产品规则之间的矛盾、测试覆盖缺口、运行时风险、业务概念和代码实体之间的关系。

L3 应该呈现为语义解释视图、任务视图或 Claim Graph。每个 L3 结论都必须能反向追踪：

```txt
answer
  -> L3 claim
  -> L2 local graph node
  -> L1 source group
  -> L0 package
  -> original source
```

## local-sbt 示例

`examples/local-sbt` 当前配置只有一个 source root：

```txt
./sources
```

编译后 source model 会把它识别成 3 个 L0 package：

```txt
L0 Package:
  - 代码仓库包: MJSBT Manage Frontend
  - 代码仓库包: MJSBT Platform Frontend
  - 产品资料包: Product Documentation
```

当前这 3 个 L0 package 各自对应 1 个 L1 SourceGroup：

```txt
L1 SourceGroup:
  - MJSBT Manage Frontend，kind=repository
  - MJSBT Platform Frontend，kind=repository
  - Product Documentation，kind=doc_bundle
```

L2 会分别围绕这些 L1 group 建局部图：

```txt
L2 LocalGraph:
  - manage-fe group -> RepositoryGraph -> File / Module / CodeSymbol / Route 图
  - platform-fe group -> RepositoryGraph -> File / Module / CodeSymbol / Route 图
  - product-docs group -> SemanticCorpusGraph -> Document / Requirement 等文档事实图
```

L3 是下一阶段语义融合目标：

```txt
L3 ClaimGraph:
  - 产品规则 -> 前端页面 -> service 调用 -> 风险或缺口
  - 需求描述 -> 代码实现 -> 测试覆盖
  - 业务概念 -> 文档证据 -> 代码实体
  - 互相支持或矛盾的规则、决策、接口和实现
```

## 当前实现状态

当前编译器已经主要覆盖 L0、L1 和 L2：

- L0/L1 source modeling 位于 `@context-compiler/core/source-model`。
- L2 graph/runtime surfaces 位于 `@context-compiler/core/graph` 和 `@context-compiler/core/runtime`。
- `ingest.local-files` 只负责本地遍历、路由和 raw artifact 读取。
- L3 Claim Graph 还没有真正实现，是后续语义层演进目标。

因此，当前 viewer 中合理期待的是：

```txt
ProjectGraph
  -> PackageGraph
    -> SourceGroupGraph
      -> RepositoryGraph / SemanticCorpusGraph / ApiContractGraph / InventoryGraph
        -> FileGraph / ContentGraph / FactGraph
```

不应该期待已经存在完整的 L3 ClaimGraph。
